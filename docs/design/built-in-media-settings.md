# Media and ad-blocking settings store

Status: isolated settings-store slice, 2026-10-13. Native settings UI and bundled component integration are pending.

## Decision

The future bundled browser component owns one versioned `chrome.storage.local` record for SponsorBlock-compatible segment preferences and the separate ad-blocking preferences. Store only global toggles, category actions, and explicit disabled-site domains; never store video IDs, visited URLs, page content, API responses, credentials, or filter packages in this record. Both features default off. Segment category defaults preserve the existing policy (`sponsor` auto, others off) but have no effect until the global segment toggle is enabled. Ad blocking has its own toggle and bounded site-exclusion list. The source of settings is trusted component UI, never a page or content script.

Before reading or writing, call `storage.local.setAccessLevel({accessLevel: 'TRUSTED_CONTEXTS'})`. Chrome documents that `storage.local` is otherwise accessible from content scripts and persists across browser restarts. A failed access-level setup or storage read must yield disabled defaults. Incognito must explicitly pass `false` to the store; any other value disables reads and writes, regardless of what is stored in a shared or split profile. A save requires a complete version-1 object with exact keys and validated values, then writes one storage key. Malformed or future-version records are not migrated silently: load returns disabled defaults and a fixed error tag. Serializing saves prevents overlapping UI actions from overwriting each other out of order within one component instance.

Host tests will cover defaults, round-trip, validation, storage failure, concurrency, and Incognito. A disposable extension in the existing source-built Chromium will check persistence after restart and that a content script cannot read the settings after access restriction. These tests do not add a Prism settings page or component. A future native UI bridge must authenticate message source, validate every requested edit, enforce the same Incognito rule, and trigger DNR reconciliation when the ad-blocking toggle/site exceptions change. The product build and Linux/Windows UI smoke tests remain gates.

Reference: [Chrome storage API](https://developer.chrome.com/docs/extensions/reference/api/storage).

## Trusted settings page prototype

Add a small options page to the prospective bundled component. It edits the two independent enable switches, each segment category's off/manual/auto action, and up to 256 excluded ad-blocking domains. The form reads and saves only through `createMediaSettingsStore`; page content and content scripts receive no settings object. Render site entries with DOM text nodes, never HTML interpolation. Validate the complete record before saving; reject malformed domains and duplicates without changing persistent settings. A failed load disables editing rather than showing editable defaults that might overwrite a damaged record.

This slice does not send a settings-change message to a worker. The page must say that saved changes take effect after component restart; a later trusted worker bridge will reload settings and reconcile DNR immediately, with explicit failure feedback. No page-visible UI is injected into YouTube. Use semantic fieldsets, labels, a live status region, visible focus, light/dark contrast, and a narrow layout. A disposable-extension browser test will check editing, invalid domains, persisted values after restart, and content-script storage denial. Native component registration and a Prism settings entry remain separate gates.

Security review: the page is an extension-origin trusted context and loads no remote scripts or styles. It never handles browser URLs, API keys, cookies, or filter packages. Domain chips are created with `textContent`; invalid and duplicate domains do not reach storage. A malformed saved record leaves every form control disabled. The existing content-script probe confirms that `TRUSTED_CONTEXTS` denies untrusted reads even after restart. A future worker notification must authenticate the extension page sender and reload settings from storage rather than accept settings in a message.

## Trusted save notification

After a successful save, the options page sends only the fixed `prism.settings.apply` message to its component worker. The message carries no settings or page data. The worker accepts it only from its own extension ID, the exact options-page URL, the top frame, and a regular profile; an origin or tab Incognito flag, when supplied, must agree. Its single rule owner reloads settings and the signed rule cache from trusted storage, then runs the existing DNR reconciliation. Rejected messages must have no storage or DNR side effects. The owner serializes startup, save, and update operations so rapid saves cannot race rule replacement. Return only a small fixed status, never package provenance or stored settings.

The options page distinguishes a saved-and-applied result from a saved-but-not-applied result. Segment preferences are read on the next lookup, while DNR changes apply after successful worker reconciliation. This is an isolated MV3 component bridge; the future bundled component must register the same worker and make it the single owner of startup, settings, and update rule mutations. Browser-native UI integration and a product build remain unverified.
